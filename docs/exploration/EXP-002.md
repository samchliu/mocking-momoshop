# EXP-002：實站觀察：固定版頭、搜尋框收合、首頁無限商品流

> ⚠️ **探索性知識。** 以下內容都是目前的看法，可能是錯的。請不要依據本文件實作；請依據它最終產出的需求文件（REQ-005）實作。

## 最初的想法

> 「我發現 momo 的一些前端設計，我們也要復刻：1. fix 的 topnav 2. search bar 會在滾出 viewport 後改到 fix 的 topnav 3. 首頁是 infinite scroll，看起來有做瀑布流載入加 virtual scrolling」
> —— PM，2026-11-20，開發對話

## 問題假設

逛首頁時，使用者往下滑仍需要隨時能搜尋、進購物車；首頁底部的推薦商品應能一直往下逛，而且滑得很深時也不卡頓。

## 觀察證據（AI 以瀏覽器量測，2026-11-20）

環境：桌機版 `www.momoshop.com.tw/main/Main.jsp`，視窗 1470×741。手機版未量測。

| #   | 觀察                                                                                                                                                                     | 與原始想法的差異                                 |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| O1  | 頂部 41px 的 bar 是 `position: fixed; top: 0`，全寬，任何捲動位置都在                                                                                                    | 一致                                             |
| O2  | 只要 `scrollY > 0`（實測 5px）搜尋框就移進頂部 bar；此時原搜尋框仍完全在畫面內                                                                                           | **不是**「滾出 viewport 才切換」                 |
| O3  | 頁面上同時只有一個搜尋 input，切換時節點被換掉（條件渲染，非搬移同一節點）                                                                                               | 實作細節；推測輸入中切換會失去焦點（未實測）     |
| O4  | bar 內容會換：頂端時是服務連結（APP 下載、書店…）；捲動後換成「回首頁＋搜尋框＋會員連結＋購物車」；bar 高度不變                                                          | —                                                |
| O5  | 首頁底部商品流：每滑到底多 20 個（4 列 × 5 欄），頁高 +1744px；載入 4 次後停止，共約 100 個                                                                              | 一致；「約 100 個上限」是推論，未看 API 回應確認 |
| O6  | 商品流容器以固定 `height` 撐出捲動範圍，卡片 `position: absolute` 用 inline `left/top` 定位；約 100 個商品中 DOM 同時只有 25–50 張，捲動時替換；DOM 節點總數不隨載入增加 | 一致：有 virtual scrolling                       |
| O7  | 所有卡片高度相同（420px），5 欄、列距 436px                                                                                                                              | **不是**瀑布流，是等高網格（用絕對定位排版）     |

## 假設

| #   | 假設                                                                                        | 信心       | 驗證方式                 |
| --- | ------------------------------------------------------------------------------------------- | ---------- | ------------------------ |
| H1  | 復刻「行為」即可：固定版頭＋捲動後搜尋框在版頭；不必複製 momo 的節點替換做法                | hypothesis | PM 確認                  |
| H2  | 等高網格的虛擬化（以列為單位）足以達成 O6 的效能目標，不需要瀑布流（O7）                    | supported  | O7                       |
| H3  | 我們的 mock 資料量（約 100 個）在不虛擬化時也不會卡；虛擬化的價值在於展示工程判斷而非必要性 | hypothesis | 實作後以 Lighthouse 量測 |
