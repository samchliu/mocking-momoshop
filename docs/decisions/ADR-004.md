# ADR-004：人機協作架構（Human-Agent Iteration）

## 背景（Context）

評分重視 AI／Agent 監督能力與「長期維護者」視角（REF-001）。AI 產出程式碼很快，風險在於：規格被 AI 悄悄改寫、程式碼偏離規格卻沒人發現、事後沒人說得出「為什麼這樣做」。

## 決策（Decision）

採用 living-kb 作為知識層，並把人機分工寫成流程與自動檢查：

```
人：EXP（探索）──升級──► REQ / BR / ADR（權威，人核准）
                               │ npx kb build
                               ▼
                     ai-context.md（只含權威知識）
                               │ 交給 agent
AI：測試（名稱含 REQ-xxx#ACn / BR-xxx#Rn）→ 實作 → 自我驗證
                               │
閘門：npm run verify（型別、lint、spec↔test 追溯、測試）
      + npx kb validate --code-root .（偏移、斷鏈、權威外洩）
                               │
人：review diff → 合併 → 把 AI 的錯誤記錄進 RPT-001
```

規則：

1. AI 只能起草（`status: draft`），**不得**填寫 `approved_by`，不得把探索性知識升級為權威。
2. Agent 只讀 `ai-context.md` 與被指派的檔案範圍；規格有疑義時回報，不自行假設。
3. 每條 AC／規則必須有測試（`spec:check`）；程式碼引用的知識 ID 必須存在且未棄用（`kb validate --code-root`）。
4. 平行 agent 數量上限 3，確保每份 diff 都能被人完整 review。

## 替代方案（Alternatives）

| 方案                          | 不選的原因                                                                       |
| ----------------------------- | -------------------------------------------------------------------------------- |
| 單一 SPEC.md                  | 需求、規則、決策混在一起，無法追蹤「改了 BR-002 會影響什麼」，也沒有負責人與狀態 |
| 只用 prompt 對話              | 決策不留存；新的 agent 必須重新推導                                              |
| 多 agent 全自動（無人工閘門） | 速度快但無法對產出負責；違反「AI 不是知識負責人」                                |

## 後果（Consequences）

- Phase 1 花較多時間在知識文件；Phase 2 的 agent 任務因此可以平行且邊界清楚。
- 每個 commit 帶 `Co-Authored-By` 與相關知識 ID，git history 本身即是協作紀錄。

## 取捨（Trade-offs）

用前期文件成本，換取可追溯性、可平行化與 on-site 時「每一行為什麼存在」都答得出來。

## 備註（只能追加）

- 2026-11-20（負責人指示，AI 記錄）：開發流程補充以下強制規則——
  1. 每個 feature 開獨立 branch 與 git worktree（`scripts/worktree.sh`），不直接在 main 上開發。
  2. 先寫測試、後實作（SDD）。
  3. commit 前必須通過 lint、typecheck、test：以 husky `pre-commit` 強制執行（另含 lint-staged 與 `kb validate`）。
  4. commit message 以 commitlint 強制 conventional commits；`feat`／`fix` 必須引用知識 ID。
  5. 全量 `spec:check` 在合併回 main 前執行；分支內以 `spec:check -- <IDs>` 檢查自己負責的範圍，避免平行分支互相阻擋。
