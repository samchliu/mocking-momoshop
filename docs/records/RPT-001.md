# RPT-001：Agent 協作紀錄與效率分析

## 目的

記錄 Phase 1／Phase 2 中人與 agent 的分工、agent 產出被修改或否決的地方，以及協作效率，作為 ADR-004 是否有效的證據。

## 環境與方法

- 工具：Claude Code（主 agent，擔任整合者）＋ 依 ADR-004 派出的 feature agent（上限 3）。
- 每個 agent 任務的輸入：`docs/_build/features/REQ-xxx/ai-context.md` ＋ 指定檔案範圍。
- 閘門：`npm run verify`（含 `kb validate --code-root .` 與 `spec:check`）＋ 人工 review diff。
- 量測：每個任務的開始／結束 commit 時間、review 中發現的問題數、退回次數。

## 結論

- **平行化有效的前提是先做共用契約。** foundation（型別、parser、mock 後端、購物車 hook、測試 harness）由整合者序列完成約 8 分鐘；之後 3 個 agent 平行約 6～8 分鐘完成各自的 REQ，三個分支合併**零衝突**。
- **知識 ID 讓 review 變成核對而不是閱讀。** 每個 agent 回報 `spec:check -- REQ-00x` 結果（7/7、7/7、4/4），整合者只需抽查規則實作與範圍邊界（scope 外檔案、跨 feature import、`any`、`useEffect`、token fallback）。
- **閘門擋下的與 review 擋下的不同。** hooks／lint 擋下格式、型別、a11y 規則；review 與量測擋下的是「規則正確但體驗有問題」（#4 連點競態、#8 對比度）和「流程本身的缺陷」（#6、#7）。
- **agent 回報的假設是最有價值的產出。** 3 個 agent 共回報 6 個規格缺口（見下），沒有一個自行發明行為。

| 規格缺口                                 | 來源         | 目前行為                                            | 需要誰決定        |
| ---------------------------------------- | ------------ | --------------------------------------------------- | ----------------- |
| 售完的規格可否被選取                     | 商品頁 agent | 可選取、顯示價格，按鈕停用「已售完」                | PM（REQ-002#AC5） |
| URL 帶非法 `sort`／`min`／`max` 是否改寫 | 搜尋頁 agent | 只改寫 `page`；非法 sort 視為綜合推薦、非法價格忽略 | RD（ADR-005）     |
| 空白關鍵字 `/search/%20`                 | 搜尋頁 agent | 顯示「請輸入搜尋關鍵字」                            | PM（REQ-001）     |
| 限時搶購開始前                           | 首頁 agent   | 原價 +「即將開始」，無倒數                          | PM（REQ-003#AC2） |
| 輪播自動切換間隔                         | 首頁 agent   | 5 秒；可暫停；reduced-motion 時不自動切換           | PM（REQ-003#AC1） |
| REQ-002#AC3 驗證位置寫 `features/cart`   | 商品頁 agent | 規則已移到 `features/catalog/purchase.ts`           | PM（文件修正）    |

## 後續

- 6 個規格缺口由負責人決定後更新 REQ／ADR（AI 只起草）。

- `LazySection` 支援響應式最小高度（首頁 agent 建議）；新增 overlay 色 token。
