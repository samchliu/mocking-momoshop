# RPT-003：規格階段的人機協作：核准前歧義檢查的效果

## 目的

RPT-001 記錄的是**實作階段**：agent 依已核准的規格寫程式，發現規格沒寫到的地方就回報（6 個規格缺口）。本報告記錄**規格階段**：AI 起草規格、在人核准之前，由乾淨 context 的 subagent 找出「實作者需要猜測的地方」。目的在回答兩個問題：

1. 核准前的歧義檢查，能不能把「實作時才發現的缺口」提前到「核准前」？
2. 檢查要跑幾輪才停？

## 環境與方法

- 範圍：CR-001（版面骨架、商品頁主區、詳情分頁）與 RPT-001 六個規格缺口的定案，共 4 批、7 份權威文件。
- 工具：專案 skill `/ambiguity-check`（`.claude/skills/ambiguity-check/`，由負責人既有的 skill 改寫為 living-kb 版本）。
  - 每份文件派一個 `general-purpose` subagent，不繼承對話 context；只能讀該文件與文件內以 ID 引用的 BR／API／ADR 條文。
  - 檢查清單在 `prompt.md`：可測性、狀態、邊界值、響應式斷點、用語一致、與被引用條文的矛盾、隱含假設。
  - 對外契約（API-001）同時派兩個獨立 subagent，兩邊都指出的視為高信心。
  - skill 唯讀：只回報，不改文件。修改由 AI 起草、答案由負責人決定，最後由人執行 `npm run approve`。
- 流程：AI 起草 → 歧義檢查 → 負責人決定答案 → AI 回填文件（寫入決定內容，不寫「依建議」）→ 再檢查或核准 → 測試先行實作。

### 3. 「把現有行為寫成規格」的情況

RPT-001 的 6 個缺口定案時，答案都是「維持目前行為」。歧義檢查仍找到 45 處；逐一對照程式碼後：

- 全部都能以程式的實際行為回答（例：使用者暫停與滑鼠移入暫停是兩個狀態、只有 1 張主視覺時不顯示控制項、勾選品牌時其他非法參數原樣保留）。
- 程式碼不需修改；補了 8 個測試（之後 AC9 例子修正再補 1 個），寫好即為綠燈（commit 訊息註明為描述現有行為的測試）。
- 有 1 處行為照實寫入但值得負責人知道：倒數以秒無條件捨去，顯示 00:00:00 的最後不到 1 秒仍為進行中（符合 BR-001#R5）。

## 結論

- **問題被提前了。** RPT-001 中 6 個缺口是在 3 個 agent 實作時才回報；本次 7 份文件在核准前共被找出 119 處需要猜測的地方（第 1 輪 41＋45＋2、第 2 輪 31；API-001 的兩個 subagent 只計一份），其中 7 處屬於「兩種實作都符合規格、但行為相反」的等級。CR-001 核准後的實作一次通過，沒有回頭改規格。
- **AI 起草的規格會自相矛盾，而且起草者自己看不出來。** 7 處重大問題中 3 處是 AI 在回填答案時引入的（#3、#4、#5）。同一個對話內的模型已經知道意圖，會自動補上空白；只有不繼承 context 的檢查者能發現。這是 skill 堅持「不得用 fork」的實際理由。
- **兩個獨立 subagent 的交集是好的信心指標。** API-001 兩輪各自的核心 4 點完全一致，其餘各報 3～6 個不重疊的細節。
- **第 2 輪之後收益遞減。** 第 2 輪問題數只降 25～30%，但性質轉為樣式與量測細節；決定在第 2 輪後停止，剩餘細節依 token 與實站量測值實作，有出入時回報 DRIFT。之後的批次只跑 1 輪，回填內容若全部來自程式的現有行為，直接核准。
- **「範例」也需要被驗證。** #6 是規則正確、例子錯誤。例子是測試的來源，應由測試反向確認（AC9 現在註明了資料前提與確認它的測試）。

## 後續

- `prompt.md` 補一條檢查項目：「文件中的例子能否在現有資料／畫面上實際操作」。
- 歧義檢查的報告目前只留在對話中（skill 設計如此）；若要追蹤趨勢，可把每次的「找到 N 處」與處理結果附在 CR 的「影響」或本類報告。
- 考慮在 `npm run approve` 前提示「這份文件跑過 /ambiguity-check 了嗎」，把慣例變成閘門。
