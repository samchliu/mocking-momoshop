# ambiguity-check — 核准前的把關

本專案的開發流程（`CLAUDE.md`、ADR-004）：AI 起草 → **歧義檢查** → 人核准（`npm run approve`）→
`kb build` 產生 `ai-context.md` → agent 先寫測試再實作。`kb validate` 只檢查結構（欄位、關係、追溯），
**不讀語意**；這個 skill 補上語意那一層：一個只拿到這份文件的實作者，會在哪裡猜錯。

> 來源：改寫自負責人原有的 `ambiguity-check` skill（v1.0.0，用於另一專案的 `docs/specs/`），
> 調整為 living-kb 的文件 ID、狀態流程與本專案的檢查項目。

## 為什麼一定要派給 subagent

檢查要問的是「一個只讀得到這份文件的人，會在哪裡猜錯」。如果在起草文件的同一個對話裡跑，
模型已經知道所有意圖、剛剛拍板了什麼、哪個詞是什麼意思——它會**自動把空白補上**，然後回報
「很清楚」。那正是最危險的結果：以為過關了，實際上只是檢查者作弊。

所以：**一律用 `Agent` 工具派給一個全新的 subagent**（`subagent_type: "general-purpose"`），讓它自己讀檔。

⚠️ **絕對不要用 `subagent_type: "fork"`**——fork 會繼承當前對話的完整 context，這個 skill 就失去意義。

⚠️ **也不要自己在當前對話裡讀完文件再檢查。** 你頂多讀 front matter 確認 ID、路徑與 `status`，內文交給 subagent。

## 這個 skill 唯讀

`allowed-tools` 刻意沒有 `Write` 與 `Edit`——不是靠自律，是結構上就改不了文件。

歧義點的正確答案往往只有人知道。模型自己把答案填進去，等於把猜測寫進了契約，而且看起來會跟人拍板的
一樣權威。這與 `CLAUDE.md`「規格沒寫到的：不要發明，列為問題回報」是同一條原則。報告完就停。

## 流程

### 1. 找出要檢查哪幾份

使用者給的可能是 ID（`REQ-004`）、多個 ID、`CR-001`（＝它 `changes` 的那幾份）、路徑，或什麼都沒給。

```bash
# 專案根目錄：從 cwd 往上找到有 kb.config.yaml 的那一層（worktree 也適用）
grep -rl "^id: REQ-004$" docs --include='*.md'
# 給了 CR：列出它改動的文件
npx kb trace CR-001
# 什麼都沒給：列出 draft／review 的權威文件
grep -rlE "^status: (draft|review)$" docs/requirements docs/business-rules docs/api docs/decisions docs/change-requests
```

- **找不到** → 列出候選，問使用者。不要猜。
- **`status: approved`** → 提醒「這份已核准」，問是否要重跑（內容改過之後重跑是合理的；核准後的修改要走 CR）。
- **`knowledge_state: exploratory` 或 `record`**（EXP／REF／RPT）→ 不檢查：它們是證據，不是規格。告訴使用者。
- **CR 本身**不檢查驗收條件（它沒有），只檢查它 `changes` 的文件；CR 的「未解問題」照列在報告最後供參考。

### 2. 取得檢查項目

**優先讀專案的檢查清單**：本 skill 目錄下的 `prompt.md`。它是單一事實來源，抽出 ` ``` ` 圍起來的 prompt 原文，原樣交給 subagent。

**讀不到時**用下面的備份，並**明白告訴使用者用的是備份**：

```
這是一份要交給 coding agent 實作的規格。請你不要開始寫任何程式碼，
只做一件事：找出這份規格中會讓實作者需要「猜測」的地方。

針對每一處，說明：
1. 有歧義的句子
2. 至少兩種合理但不同的解讀
3. 你會建議怎麼改寫

特別檢查：
- 有沒有形容詞式的需求（「快速」「順暢」「合理」「約」）沒有量化
- 錯誤處理是否只寫了 happy path
- 資料的邊界值（空、極大、null、重複）有沒有定義
- 有沒有隱含假設我沒寫出來但你補上的

最後列出你認為最可能被實作錯誤的三個地方。
```

### 3. 派出檢查者

每份文件派一個 subagent（`general-purpose`），彼此獨立、可以平行。prompt 要包含：

1. **文件的絕對路徑**，要求它自己完整讀完（不要貼內文——貼的過程會不自覺摘要或跳過，被跳過的往往正是模糊的地方）
2. **`prompt.md` 的 prompt 原文**
3. **隔離聲明**：

   > 你只能依據這份文件本身判斷。不要去讀程式碼、`CLAUDE.md`、`docs/_build/`、README，
   > 或其他未被引用的文件來替它補完——那正是我們要測的：一個只有這份文件的實作者會在哪裡卡住。
   > 唯一的例外：這份文件在驗收條件／規則表的「規則」欄、或內文中**以 ID 明確引用**的
   > BR／API 文件（例如 `BR-003#R2`、`API-001`），可以讀被引用的那一條，因為它是同一份契約的一部分。
   > 路徑：`docs/business-rules/BR-xxx.md`、`docs/api/API-xxx.md`。

   給了 Read 與 Grep，它的本能是把上下文補齊，然後回報「都很清楚」。這條要寫明。

4. **輸出格式**（見下一節）
5. **報告語言：繁體中文**
6. 若文件是「修改後待重新核准」（`status: review`），告訴它**只看變更歷史最後一列提到的新增／修改部分**是否有歧義，舊條文只在與新條文互相矛盾時才報。

> **要跑兩輪嗎**：預設一輪。文件動到**對外契約**（API-xxx）或**金額／庫存規則**（BR-001、BR-003），
> 或使用者說「跑深一點」「跑兩輪」時，**同時派兩個獨立的 subagent**（同一個 prompt，不互看結果），
> 合併時**兩邊都指出的標為高信心**。

### 4. 回報

結果**直接寫在對話裡**，不落檔。每份文件一段：

```
## 歧義檢查：<ID> <標題>

檢查者：乾淨 context 的 subagent（1 輪／2 輪）｜檢查項目來源：<專案 prompt.md／內建備份>｜範圍：<全文／變更部分>

**找到 N 處需要猜測的地方。**

### 最可能被實作錯誤的三個

1. **<一句話講清楚是什麼>**（<AC 編號或章節>）
   - 原文：「<照抄>」
   - 解讀 A：… ／ 解讀 B：…
   - 建議：…

### 其餘 N-3 處

| # | 位置 | 問題 | 建議 | 能自己改／要問人 |
|---|---|---|---|---|

### 下一步

1. 能自己改的：AI 起草修正（文件維持 draft／review），再重跑本檢查
2. 要問人的：寫進該文件的「未解問題」；需要問外部的，起草 CLR（`templates/clarification.md`）
3. 都處理後，由負責人執行 `npm run approve -- <ID>`（AI 不得代為核准）
```

三個原則：

- **原文照抄**，不要改寫。使用者要能 Ctrl+F 找到那一句。
- **標 AC／R 編號或章節**，讓他直接跳過去改。
- **分開「能自己改的」與「要問人的」**。後者不是缺陷，是「未解問題」該有的內容——混在一起會讓人以為全都要在核准前解決。

若一處都沒找到：直說，並提一句這通常代表兩件事之一——文件真的寫得夠死，或太短、還沒具體到會產生歧義。

## 不要做的事

- **不要改文件**（結構上也改不了）。連錯字都不要。
- **不要用 `fork`** 當 subagent_type。
- **不要替使用者決定歧義點的答案。** 「我覺得應該是 A」跟「這裡有 A/B 兩種解讀」差很多。
- **不要把檢查結果直接寫進「未解問題」。** 那是使用者篩選過之後才該進去的東西。
- **不要在報告裡摻入對功能的意見**（架構建議、技術選型）。這個 skill 只回答一個問題：哪裡會被猜錯。
- **不要用它取代 `kb validate`**——結構問題（缺欄位、壞連結、沒有 verified_by）交給 validate。
