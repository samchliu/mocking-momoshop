# 歧義檢查 prompt（本專案的檢查清單，單一事實來源）

`SKILL.md` 會抽出下方 ` ``` ` 內的原文交給乾淨 context 的 subagent。要增減檢查項目就改這裡。

```
這是一份要交給 coding agent 實作的規格（living-kb 權威文件：REQ／BR／API／ADR）。
請你不要開始寫任何程式碼，只做一件事：找出這份規格中會讓實作者需要「猜測」的地方。

針對每一處，說明：
1. 有歧義的句子（原文照抄，標出 AC／R 編號或章節）
2. 至少兩種合理但不同的解讀
3. 你會建議怎麼改寫
4. 這一處是「作者能自己改清楚」，還是「需要問負責人／外部才知道答案」

特別檢查：
- 形容詞或約略詞沒有量化：「快速」「順暢」「合理」「約」「適當」「左右」「等」——測試要怎麼判斷通過？容許誤差多少？
- 驗收條件是否可測：每條 AC 有沒有可觀察的結果（畫面文字、URL、請求次數、角色／屬性）？「看起來像」不可測。
- 狀態是否只寫了 happy path：載入中、失敗（4xx／5xx／逾時／離線）、空資料、重試、連點、慢速網路。
- 邊界值：0、空字串、空陣列、null、極大值、重複值、非法輸入；數量與金額的上下限；時間區間是開區間還是閉區間。
- 響應式：「桌機／手機」的斷點寬度是否明確？斷點上剛好等於時屬於哪一邊？
- 用語一致：同一個概念是否用了不同名稱（例如「規格」同時指商品規格表與可選的 variant）？
- 與被引用的 BR／API 是否矛盾：AC 的「規則」欄引用的條文，和 AC 文字描述是否一致？欄位名稱、型別、可否為空是否對得上？
- 範圍：「範圍內」與「不在範圍內」有沒有互相衝突或漏掉的灰色地帶？
- 有沒有隱含假設——我沒寫出來，但你為了實作必須自己補上的？

最後列出你認為最可能被實作錯誤的三個地方。
```
